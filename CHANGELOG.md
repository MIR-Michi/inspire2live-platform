## [Unreleased]

### Security
- **The five scheduled routes were reachable by anyone, and are now closed.** Each guarded itself with `if (expected && provided !== expected) return 401` — a check that is **conditional on the secret existing**, so with `CRON_SECRET` unset the comparison never ran and every caller was treated as the scheduler. `CRON_SECRET` was unset in production: an anonymous `GET /api/comms/digest` answered **200**. Because these routes hold the service-role client, that exposed unauthenticated **email sending** (the digest, to every comms user due one) and unauthenticated **AI spend** (the newsfeed, conference discovery and Radar jobs, each with a 300-second budget), plus the retention purge. The guard is now one kernel function, [`denyUnauthorizedCron`](src/kernel/identity/cron-auth.ts), which **fails closed**: no secret, no run. It answers **503 rather than 401** when the secret is absent, because in that case the caller is fine and the server is misconfigured — and a cron going red in the dashboard is how an operator finds out. Tokens are compared as digests, in constant time. **Set `CRON_SECRET` in Vercel: until it exists the scheduled jobs are off rather than open.** Three things let this survive — the tests set the secret in every case and only ever presented a *wrong* one, so the shipped branch was never executed; `ENVIRONMENT_REFERENCE.md` had always documented the 401-when-missing behaviour that the code did not implement; and Sprint 22 noticed the fail-open idiom and filed it as a note about the pattern rather than as live exposure. Full account: [`docs/changes/2026-08-21-cron-auth-fail-closed.md`](docs/changes/2026-08-21-cron-auth-fail-closed.md).

### Added
- **Sprint 22 — Podcast Radar (Phase B): the board gets a front door.** Until now the planner had no way to add a candidate at all — `addCandidate` and `network.createPerson` were implemented, exported and called by nothing. Radar closes that, in two shapes. **"Suggest guests"** on a live question reads open scholarly catalogues and comes back with named people, each with the record that names them and one sentence on what only they could say. A **fortnightly scan** (`/api/comms/podcast/radar`, cron) groups what is being published into *questions the podcast could ask* and proposes them on a new **Radar** tab, badged with how many are waiting. Either way the reviewer sees one card and makes one gesture: tick the names worth having and accept, or dismiss with one of three reasons.
  - **The model never sources a fact a database can supply ([ADR-0016](docs/ADR/0016-radar-structured-sources.md)).** Names, affiliations, papers and dates come from **OpenAlex** and **Europe PMC** through new kernel clients (`@/kernel/sources`); the model is handed records that were already retrieved and asked only to group and phrase them. It refers to people by reference (`p3`) and never writes a name, and any suggestion that cannot be resolved back to a supplied record is **dropped before review** rather than flagged — a confidence badge is something reviewers learn to ignore, an absence is not. "Three independent sources" is therefore a count of rows, computed over shared authorship, with papers both catalogues indexed collapsed by DOI first so one paper cannot be counted as two.
  - **Accepting writes four things and nothing else.** People through `network`'s public API (with per-field source attribution, no contact details), a question as a **draft** so the existing readiness gate still applies, one **unscored** wishlist card per ticked name, and the proposal marked as acted on. Radar never writes a score, a listener action or any stage past Wishlist, and `origin`/`radar_proposal_id` on the card keep it attributable to the run that suggested it.
  - **Dismissals are the only learning.** The three reasons are fed back into the scan's **cached** prompt prefix as rejected examples — stably sorted and capped so the prefix is byte-identical between lanes and runs, and billed once. There is no learned threshold and no scoring model.
  - **The first spend ceiling in the codebase.** `ai_usage_log` has been written by every AI call since Sprint 14 and read by no decision. A scheduled scan now checks the trailing thirty days against an operator-set ceiling, plus a hard per-run search cap, and **refuses out loud** — writing the reason into the run status the Radar screen displays, because a scan that stops quietly looks exactly like one that has been broken for a month.
  - **Retention, finally implemented.** The engine concept promised the Board an eighteen-month purge of inactive people records and twelve-month anonymisation of closed cards; no retention job of any kind existed. Both now run weekly (`/api/comms/podcast/retention`), with a dry-run mode, exemptions for members, CRM contacts and anyone on a live card, and no resurrection of a purged record.
  - **A line in the daily digest** — "Radar has N new topics to look at" — linking straight to the tab, so the review does not depend on remembering to visit it. The digest gained a generic `highlights` slot for this rather than any knowledge of podcasts.
  - Migration `00175` adds `podcast_radar_signals`, `podcast_radar_proposals` and `podcast_radar_status`, all comms-team-only. Two indexes carry rules rather than speed: signals are unique on their dedupe key so re-running a search converges instead of accumulating, and a partial unique index allows only one pending proposal per question so a second run supersedes the first rather than stacking a card on the reviewer. See `docs/PODCAST_RADAR_CONCEPT.md` and [`sprints/sprint-22-podcast-radar/`](sprints/sprint-22-podcast-radar/description.md).
- **Sprint 21 — The Publishing space (LinkedIn first).** A **Publishing** space at `/app/comms/publishing` turns either a platform record **or** a dropped screenshot plus one line of context into channel-ready copy, on one screen with three steps: source · draft · approve. Two ways in are weighted equally — pick a recent World Campus session, or drop an image and describe it — and both arrive at the drafter as the same payload.
  - **A source is a curated payload, never a page read.** Each owning component exports a `SourceProvider` and declares it through the new optional `provides.sources` manifest field; only publication-intended fields leave the component, so a session's transcript, WhatsApp digest, attendee list and internal comments are never sent to the model. An uploaded screenshot goes through the *same* contract rather than a second code path, and therefore inherits the same readiness, groundedness and approval gates.
  - **Drafting you can audit.** Variants come back with an angle, a character budget from the channel profile, hashtags, and **every factual claim mapped to the source field it came from** — a citation naming a field that was not sent fails validation and nothing is written. For an image source the model's own reading is shown in the review, so a misread is caught before approval. The kernel AI client gained image input for this (`AiMessage.content` accepts content blocks; images are encoded server-side and never round-trip through the browser) on the new `channel_post_draft` workload.
  - **A review that is a real review.** In-place editing with a divergence marker, an explicit approval that stamps who approved what and dismisses the siblings, and an untouched `ai_body` kept beside the edited text for calibration. Regenerating supersedes the previous run, and a partial unique index enforces at most one live pending run per source and channel.
  - **A handover, not a dead end.** Approved copy becomes a `content_calendar` entry through `content`'s own action, the entry id is written back onto the source by the provider's `onPublished` hook, and a delivery intent is logged. An ad-hoc upload carries a rights answer; anything not cleared for publication can be drafted from but **cannot** hand over.
  - **One generic component with an extension point (ADR-0014).** `publishing` (migration `00173`) imports the kernel and `content@^1` only — composition lives in `src/modules/publishing-registry.ts`, and a new source-reconciliation governance gate fails on a declared-but-unregistered source, an unregistered-but-declared provider, or a wrong `ownedBy`. A channel is **data** keyed by the existing `CalendarChannel` vocabulary (LinkedIn enabled; newsletter and website visible and deliberately unavailable), so there is no `linkedin` module. Every tunable — variants per run, brand voice, banned phrases, hashtag policy, readiness threshold, upload ceiling, stale behaviour — is manifest `config` in Platform Settings, **except** human approval before handover, which is fixed in the domain layer and is not a setting. See `docs/PUBLISHING_SPACE_CONCEPT.md`, [ADR-0014](docs/ADR/0014-publishing-space.md) and [`sprints/sprint-21-publishing-space/`](sprints/sprint-21-publishing-space/description.md).
- **Saved posts in the Publishing space — a post you own, not just a draft you approved (migration `00174`, [ADR-0015](docs/ADR/0015-saved-posts.md)).** A generated variant can now be **saved** at any point, finished or not, and it becomes a **post** that survives the wizard: the space's landing page shows the saved posts as **tiles** (filterable by status and by "Mine"), and each opens an editor at `/app/comms/publishing/posts/[id]`.
  - **Editable afterwards, picture included.** Body, title and hashtags stay editable for the whole life of the post, and a picture can be added, replaced or removed at any time — previously the image belonged to the *source* and could never be changed once drafting had happened. Only pictures the post uploaded itself are deleted on replace; a shared source image is left alone.
  - **Three states in the user's language.** `draft → ready to publish → published`, and backwards again. **`Published` is a human statement that the copy went out** — the platform has no channel connector and never sets it by itself. Approving a variant now also creates its post, arriving *ready to publish*.
  - **An owner, shown and reassignable.** `owner_id` says who is responsible and can be handed to a colleague; `created_by` records who made it and never changes. Access stays team-wide — ownership is responsibility, not permission.
  - **Handover moved from the draft to the post,** amending [ADR-0014](docs/ADR/0014-publishing-space.md) §6: because a post keeps changing after approval, handing the frozen draft to the calendar would have put pre-edit text there. The calendar entry now carries the post's current body and the **owner** as its author. The rights gate widened with it — uncleared material can no longer be marked ready to publish, marked published, *or* handed over, still through a single chokepoint that no setting can disable.
  - `publishing_drafts` is untouched: it stays the frozen calibration record with `ai_body` beside the approved text, which is exactly why the post is a separate table rather than a looser draft.
- **Sprint 20 — Podcast Opportunity Engine (Phase A).** The podcast **Guests** tab is replaced by a **Planning & Strategy** planner at `/app/comms/podcast?tab=planning`: live questions, a wishlist of people per question, a six-stage board (Wishlist · Research · Ask · Planning · Booked · Recorded, plus *Not now* with a wake date and *Closed* with a reason), and a relationship map that finds the shortest warm route to each person. Nothing is deleted — past guests are imported (idempotently) into the People list, where a proven willingness to appear makes them the strongest available introducers.
  - **Gates that hold in the domain layer, not just the form.** No candidate leaves the wishlist until its question has a listener action and a destination; Ask needs an angle, a route and a score; Booked needs a date, consent, and every seat filled for a two-voice format. **Six open asks across all questions is the working ceiling** — chasing is capped, research is not.
  - **An explainable score.** 100 points from six parts (chance of a yes 25 · reach 20 · timeliness 20 · follow-up 15 · mission 15 · format 5), breakdown always shown, timeliness decaying by half-life so stale names sink without pruning, and an override that is recorded rather than hidden. Scoring is plain arithmetic over stored fields and every computation is snapshotted with a `weights_version` (`podcast_candidate_scores`) so any number can be reproduced.
  - **A network map built without scraping anything.** Members declare contexts opt-in, item by item, revocably; overlaps produce *guesses*, a five-second "do you know them?" question turns a guess into a confirmed connection, and only then does the favour go out. Two-step routes take the 15 % discount, routes below 0.20 are never offered, and no introducer receives more than one favour request per fortnight. Request history is shown as recognition, never as a leaderboard.
  - **Two components, split along the reuse seam (ADR-0013).** `network` (migration `00171`) owns the generic relationship graph and the introduction protocol and depends only on the kernel + the identity spine; `podcast-planning` (migration `00172`) owns the editorial domain and reads people through `network`'s published `security_invoker` view with **no cross-component foreign key**. Every threshold in both is manifest `config` — editable in Platform Settings, and the fields a blueprint would set per tenant. See `docs/PODCAST_OPPORTUNITY_ENGINE_CONCEPT.md`, `docs/ADR/0013-opportunity-engine-components.md` and `sprints/sprint-20-podcast-opportunity-engine/`.
- **Typed access to component-owned tables (`@/kernel/data` → `moduleClient`).** A component declares the row shapes it owns and gets a fully typed Supabase client for them, so a migration and its code can ship together without `(supabase as any)` at every call site (AGENTS.md §11). One documented cast, in the kernel.

- **A watchable "How it works" tour in the Podcast space.** A "How it works" button in the space header opens a self-playing walkthrough — **twenty-seven scenes in seven chapters, about nine minutes** — that plays like a video: story-style progress bars, play/pause, previous/next, a **chapter rail** to jump between subjects, keyboard control, **three sizes** (remembered per browser), and **voice narration** spoken aloud by the browser's built-in speech synthesis in a male voice at a deliberately slow, calm rate (mutable with a speaker button; a scene holds until its sentence finishes; no audio assets to go stale). It is a walkthrough of **the product itself**: half the scenes put the real Questions screen, board, candidate drawer, route explorer and People directory on stage — populated with one worked example that runs the whole way through, and **zoomed** into whatever is being talked about — so the tour cannot drift from the UI it explains. The rest are drawings, used only where there is no screen to point at. It explains the *reasoning* as well as the buttons: why it starts with a question rather than a name, why the card is the person and the question the folder it sits in, why we work the Inspire2Live network outward before going cold, how Radar finds people from the open scholarly record — the real Radar review is on stage, and the rule that the model never sources a fact a database can supply gets a scene of its own — why chasing is capped at six open asks while thinking is unlimited, and why the score ranks but never decides. Never auto-plays. See `docs/changes/2026-08-20-podcast-onboarding-tour.md`.

### Changed
- **The "How it works" tour is now spoken by a presenter, not read out by a document.** The narration is rewritten end to end for the ear rather than the page: contractions, one idea per sentence, and the reason given before the mechanism, so the logic lands rather than merely being stated. The voice is **male** and chosen deliberately — the neural voices first, and resolved after the browser has finished loading its voice list, because reading that list too early silently falls back to the platform default. ### Fixed
- **"Suggest guests" crashed on the first reply a model ever sent.** Radar asked the kernel AI client for structured output — which means the client parses the JSON and hands back an **object** — and then tried to parse it again as text. The compiler agreed with the mistake, because `AiRunResult<T>` defaults `T` to `string`, and the unit tests shared it, because every one of them passed a string. So all five gates were green and the feature failed the moment it met a real provider, with `a.trim is not a function` shown to the user. Radar now takes `runAiMessage<unknown>` like every other AI feature in the codebase, `parseJsonReply` accepts either shape, and the stored diagnostic no longer assumes text either.
- **One throttled catalogue no longer takes "Suggest guests" down with it.** Find-names read OpenAlex alone, so an anonymous-pool `429` (sometimes served as a `503`) failed the whole click while Europe PMC was answering normally. It now queries both catalogues and settles them independently, exactly as the fortnightly scan does, and gives up only when *both* fail. Related: `OPENALEX_CONTACT_EMAIL` — which buys the polite pool and avoids most of that throttling — was read by the code but documented nowhere; it is now in `.env.example` and [`ENVIRONMENT_REFERENCE`](docs/ENVIRONMENT_REFERENCE.md).
- **The verify-before-commit gate now runs the check CI actually runs.** AGENTS.md §5 said `pnpm test`; CI runs `pnpm test:coverage`. A change can therefore add code faster than it adds tests, pass every local gate, and still fail CI on the 60% global coverage threshold — which is exactly what Radar did (58.77% lines, with all 762 tests green). §3/§5 now name `test:coverage` as the gate and say why. The coverage itself was repaired where it mattered rather than by moving the line: the **OpenAlex and Europe PMC clients went from 10% to 98%**, covered by 24 fixture-based tests with `fetch` stubbed — these two files are the provenance every Radar citation rests on, so a silent parsing failure there does not degrade a suggestion, it fabricates one. Radar's Supabase reads and writes, its settings resolver, the run-lock and its orchestration wiring are excluded in `vitest.config.ts` under the rule Sprint 20 wrote for those layers, because the decisions they used to hold now live in pure files covered at ~100%.
- **A global CSS rule was hiding real content, not just decorative subtitles.** The visual-UX pass added a rule that hides any small grey paragraph immediately following a heading. It matches on shape, so it also swallowed content that merely looks like a subtitle — including **the sentence a Radar proposal is justified by**, which meant the evidence behind every suggestion was invisible on the Radar tab, and the **caption under each scene of the podcast tour**, which left a muted viewer with a title and nothing else. Both now opt out with `data-copy`, and the rule carries a comment explaining the escape hatch. Other paragraphs still caught by it (a person's role in the People directory, several counts and timestamps) are **not** changed here — see the note in `docs/changes/2026-08-21-radar-in-the-tour.md`.
- **The podcast retention dry run no longer deletes.** `/api/comms/podcast/retention` recognised only `?dryRun=1`, so the spelling most people reach for — `?dryRun=true` — ran a **live purge** while the caller believed they were rehearsing. The parameter's presence now means rehearse and only `0`, `false` or `no` overrides it, and the card-anonymisation half reports what it *would* touch instead of skipping, which is what makes the rehearsal worth running before the first real purge. Found by calling the route rather than by testing it; the domain function had been correct all along.
- **The Radar scan stops costing two queries to say "AI is off".** Its cheapest gate — an environment read — ran *after* the config load and the interval check, despite the route documenting the gates as cheapest-first, and then answered `503`, which would have shown a failed cron every week on any deployment with AI disabled. The flag is now checked first and reports a clean skip: a switched-off feature is not an incident.
- **The dead-code governance gate now runs on Windows.** `governance-dead-code.test.ts` built its import alias as `'@/' + path.relative(...)`, which yields `@/lib\notify` on Windows and matches no real import — so every file under `src/lib` and `src/components` was reported as dead code and the gate failed for anyone running it locally on Windows. Paths are normalised to POSIX separators before matching; behaviour on Linux/CI is unchanged.
- **Dashboard design editing is stable and clear.** Fixed the white overflow strip that could appear during dashboard editing, corrected organization Design settings persistence for kernel rows (migration `00169`), and redesigned the live preview to identify and highlight the exact changed setting. Tile arrangement now starts only from a dedicated drag handle, shows large before/after/end drop targets, prevents double moves from bubbling drop events, and aligns insertion positions with the visible tiles. Keyboard and touch move controls remain available.
- **Conference list duplicates — root-caused and prevented (migration `00167`).** The master list accumulated duplicates because three insert paths each computed a *different* dedupe key for the same event: AI discovery (`slug(name):YYYY-MM`, month-precise + title-sensitive), guest resolution (`guest-…`, migration 00112), and seed/manual. So "ESMO Congress 2026" and "ESMO Congress" (dated a month off, added by a guest) landed as separate rows. The fix is one **source-agnostic canonical key** — normalise the name (drop the trailing year, ordinal edition markers like "24th", and low-signal stopwords) and key on the conference **year** so month drift and title variants no longer split — enforced by a **BEFORE INSERT/UPDATE trigger + unique index** so the database computes the key for *every* future insert (AI, guest, seed, manual) and rejects duplicates. The migration also backfills the key and **merges existing duplicates**, re-pointing all dependent rows (tracking, prep, assignments, tasks, guest submissions/tokens/invites) onto a single survivor. The app-side key (`conferenceDedupeKey`) matches the SQL. Verified end-to-end against an ephemeral Postgres: 5 seeded cross-source duplicates collapsed to 2 with zero orphaned dependents, and a subsequent guest-style duplicate was auto-rejected by the trigger.
